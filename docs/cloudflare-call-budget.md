# Cloudflare 调用预算（代码静态估计）

本页按仓库配置与本地测试估计调用路径；**未查询 Cloudflare 账户的实际用量、计费行数或费用**。浏览器活跃人数、RSSHub 路由命中率、D1 行计费和跨机房缓存命中率均未知，不据此声称费用下降百分比。

| 路径                          | 配置频率与现有复用                                                                                      | 本次处理                                                                                      |
| ----------------------------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 主 API BTC 模拟与自动交易轮次 | `*/5 * * * *`，每天 288 次定时触发                                                                      | 保持交易轮次、订单、权限审计与账本时序                                                        |
| 主 API 量化快照               | 工作日 UTC 10:45 与 23:45，各一次；四个公开 JSON 源在边缘使用 300 秒缓存；快照 payload 未变才避免新增行 | 保持源抓取与快照语义，不以跳过事件替代快照                                                    |
| 私有 KOL 同步                 | 每小时第 15 分钟，一天 24 次；失败按 1、2、4、6 小时退避，旧内容保留                                    | 每订阅读一次已有条目 ID 与 URL，只插入新条目，有新增才做 100 条保留清理                       |
| 公开研究 API                  | Worker 的配置缓存为 60 秒；前端仅对三个公开路径保留 60 秒会话内副本                                     | 不扩大缓存范围或金融报价有效期                                                                |
| KOL 浏览器读取                | 可见页面每 5 分钟读取一次，返回私有数据且 `no-store`                                                    | 允许的来源的 CORS 预检声明最长 86400 秒；浏览器实际保留时间由浏览器决定，GET 响应仍不共享缓存 |

以**一名用户的 20 个已启用订阅、每个 Feed 12 条的 ID 与 URL 均未变化**为例，旧 KOL 路径每轮向 D1 提交 240 个 `INSERT OR IGNORE`、20 个状态 `UPDATE` 与 20 个清理 `DELETE`，共 280 个 SQL 语句；新路径提交 20 个已有 ID/URL `SELECT` 与 20 个状态 `UPDATE`，共 40 个 SQL 语句。这个例子的查询每订阅返回 12 行；若条目 ID 或 URL 变化，读取行数可能不同。这是 SQL 语句数估计，D1 实际按读取与写入行等维度计量，不能从语句数直接换算费用。若每条均为新内容，仍需插入和清理，且多了已有 ID/URL 查询，因此首轮或大量新内容时未必省 D1 成本。表结构已禁止同一用户重复订阅相同 Feed URL，故没有增加无效的同 URL 抓取缓存。

本地回归测试记录了三个订阅、两个用户的模拟轮次：第一轮抓取 3 次、插入 36 次、清理 3 次；第二轮条目 URL 不变时抓取仍为 3 次，插入与清理均为 0，即使源修改了某条的 ID。模拟 Feed 失败后状态为 `stale`、12 条旧内容仍在，退避期过后下一轮恢复为 `ok`。这验证的是代码路径与操作数，不是线上调用或费用。D1 优化不会减少每小时 KOL 定时触发的 Worker 调用；边缘 Cache API 命中也仍会产生 Worker 请求。CORS 预检只可能减少浏览器实际发送的 `OPTIONS` 请求数。
