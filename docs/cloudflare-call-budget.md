# Cloudflare 调用预算与 D1 实测

下列调用路径与 KOL 示例为代码静态估计；2026-10-29 的 D1 线上实测单独记录于文末。浏览器活跃人数、RSSHub 路由命中率和跨机房缓存命中率均未知，不据此声称账户总费用下降百分比。

## 2026-10-29：BTC 验证查询读取量

远程 D1 Query Insights 的过去 24 小时中，`consensusStudy` 与 `strategyComparison` 两条查询分别累计读取 1,995,788 和 1,943,342 行，执行 295 和 298 次。此为滚动窗口，不等同于账户 UTC 自然日总用量。

已直接在远程 `web3-quant` 应用 `0038_btc_auto_completed_evaluation_indexes.sql`，只新增两个成熟结果的部分覆盖索引。Worker SQL、统计样本选择、权限及五分钟交易轮次未修改。未来正常执行迁移时，`IF NOT EXISTS` 可安全重复应用。创建索引本身一次性读取 26,536 行、写入 376 行；以后涉及索引字段的写入也会有少量额外成本。

同一份原 SQL、模型 `btc-signal-model-v2`、费用阈值 0.12、regime 为 NULL 的即时对照：

| 查询 | 优化前 rows_read | 优化后 rows_read | 返回结果 |
| --- | ---: | ---: | --- |
| consensusStudy | 6,817 | 635 | 完全一致 |
| strategyComparison | 6,706 | 352 | 完全一致 |

这两次查询合计读取量下降约 92.7%，不是账户总费用或总读取量的下降比例。查询计划确认原 SQL 自动选用新索引；无需部署 Worker。历史已消耗配额不会退回，后续实际每日用量仍需从 D1 指标核对。

以**一名用户的 20 个已启用订阅、每个 Feed 12 条的 ID 与 URL 均未变化**为例，旧 KOL 路径每轮向 D1 提交 240 个 `INSERT OR IGNORE`、20 个状态 `UPDATE` 与 20 个清理 `DELETE`，共 280 个 SQL 语句；新路径提交 20 个已有 ID/URL `SELECT` 与 20 个状态 `UPDATE`，共 40 个 SQL 语句。这个例子的查询每订阅返回 12 行；若条目 ID 或 URL 变化，读取行数可能不同。这是 SQL 语句数估计，D1 实际按读取与写入行等维度计量，不能从语句数直接换算费用。若每条均为新内容，仍需插入和清理，且多了已有 ID/URL 查询，因此首轮或大量新内容时未必省 D1 成本。表结构已禁止同一用户重复订阅相同 Feed URL，故没有增加无效的同 URL 抓取缓存。

本地回归测试记录了三个订阅、两个用户的模拟轮次：第一轮抓取 3 次、插入 36 次、清理 3 次；第二轮条目 URL 不变时抓取仍为 3 次，插入与清理均为 0，即使源修改了某条的 ID。模拟 Feed 失败后状态为 `stale`、12 条旧内容仍在，退避期过后下一轮恢复为 `ok`。这验证的是代码路径与操作数，不是线上调用或费用。D1 优化不会减少每小时 KOL 定时触发的 Worker 调用；边缘 Cache API 命中也仍会产生 Worker 请求。CORS 预检只可能减少浏览器实际发送的 `OPTIONS` 请求数。
