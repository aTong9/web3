# 数据更新卡住后的恢复边界

GitHub Actions 的九条数据更新任务各有自己的并发组。单条任务运行超过下表上限会失败并释放执行位置；下一次排程或手动运行会从当时分支的最新快照重新采集。排程时间是 UTC，GitHub 可能延迟或跳过一次计划运行，因此不能把 cron 当作精确定时或漏期补偿。

| 任务         | UTC 排程            | 最长运行 | 写入数据                                                             |
| ------------ | ------------------- | -------: | -------------------------------------------------------------------- |
| 全球市场新闻 | 每 15 分钟          |  12 分钟 | market-news                                                          |
| 美股热门股票 | 工作日 10:20、22:30 |  90 分钟 | hot-stocks、us-megacaps、美股技术信号、可选期权市场                  |
| A 股行业基金 | 每天 10:30          |  45 分钟 | a-share-sectors、technical-funds                                     |
| 美股相关基金 | 每天 01:15          |  45 分钟 | us-funds、technical-funds                                            |
| 美股指数研究 | 周二至周六 02:30    |  60 分钟 | us-index-research、us-index-daily                                    |
| 跨资产面板   | 工作日 23:20        |  60 分钟 | cross-asset、market-home、预测历史、技术事件、资产技术信号、资金传导 |
| 挪威主权基金 | 周一 03:15          |  60 分钟 | norway-fund-snapshot                                                 |
| Reddit 监测  | 每天 01:00          |  30 分钟 | reddit-monitor                                                       |
| KOL 开发快照 | 仅手动触发          |  45 分钟 | kol-monitor                                                          |

每条任务先采集并校验，失败时保留已提交的旧快照，不会把空结果当成成功更新。提交时若其他任务先写入同一分支，会有限次获取最新提交、重放本次变更并重试推送；仍冲突或重试耗尽则失败告警，不强制覆盖。两条基金任务同时碰到 `technical-funds` 冲突时，会用最新的美股与 A 股源文件重新生成并校验投影。其他同文件冲突不会自动选择一方。

“补更”指下一次运行重新请求数据源当前可提供的历史窗口。历史行情若接口仍返回遗漏区间，可被重新纳入；仅返回最新条目的 RSS 或新闻源（例如只给最近 12 条）无法保证补齐窗口外的旧内容，也不能重建已丢失的事件流水。静态人口、品牌、导航等人工维护数据不受这些 cron 自动抓取。这里不改变五分钟量化交易、订单、账本或模拟交易时序。

Cloudflare Worker 的 Cron、D1 写入与调用费用是另一条链路；GitHub Actions 的队列和提交修复不控制 Worker 的触发频率或费用。排查时分别查看 GitHub Actions 运行结果及快照时间、Cloudflare 的 Cron/调用记录，不能以一边成功推断另一边成功。
